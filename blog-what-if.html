Why What-If should be the first step, not the last check

A preview is most useful before a change feels inevitable. It creates room to investigate assumptions, confirm scope, and get approval while no data has been touched.

The dangerous shortcut

Administrative work often begins with a reasonable request: give this user the same access as that user, match a test team to production, reassign a former employee's records, or import a corrected CSV. The risk comes from treating the request as proof that the proposed change is correct. Environment selection, inherited roles, ownership scope, duplicate rows, and stale assumptions can all expand the impact.

A four-stage workflow

  1. Investigate. Use read-only reports to establish current state.
  2. Preview. Enable What-If and run the exact intended operation.
  3. Review. Check environment, identities, counts, conflicts, and exceptions with the requester or owner.
  4. Execute and verify. Turn off preview only when authorized, make the change, then rerun the report.

What What-If does not replace

A preview does not replace a sandbox, Dataverse backup, change ticket, least-privilege account, or human review. A tool can show what it intends to do, but only the administrator knows whether the request is appropriate for that organization.

Practical habit: capture or export the preview and attach it to the change record. After execution, capture the same report again. The pair documents intent and outcome.

Where to apply the pattern

Dynamic Dynamo Kit uses preview and confirmation across onboarding, offboarding, access copy, mass reassignment, team-role synchronization, bulk import, environment promotion, and other supported writes. The CLI also refuses mutating commands unless you provide --confirm or --what-if.
